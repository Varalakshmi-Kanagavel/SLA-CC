# Research methodology

## Problem and baseline

A conventional Horizontal Pod Autoscaler reacts to a fixed CPU utilization target. This baseline can be compared with a controller that adjusts the CPU target in response to latency relative to an application SLO.

## Paper-inspired approach

The demonstration starts from a configured CPU threshold. It lowers the threshold by a configurable step when latency crosses warning or critical multiples of the SLO, and raises it slowly when latency remains below 80% of the SLO. A min/max clamp prevents the target leaving the configured safe range. This is a transparent, paper-inspired example, not an exact reproduction of a particular research paper.

## Evaluation

Both algorithms receive the exact same deterministic user sequence. Compare average and p95 response time, SLO violation fraction, CPU utilization, average and peak replicas, and scaling events. Each step is generated by a deliberately simple synthetic model. These numbers are not cluster measurements and must not be presented as production results.

## Limitations

The model omits Kubernetes control-loop sampling, real pod startup, request queues, heterogeneous nodes, and measured application behavior. Scaling cooldown is simplified. The simulated scaling decisions are useful for illustrating hypotheses; validate them against a real cluster before drawing deployment conclusions.
